# Mario Kart World (`0400C3F00006E000`)

A Switch 2 game: version 1.8.0, from a dump of one Application content (version 0) that carries the 1.8.0 code and data, with no separate update. SDK 21.4.0 built for the Switch 2 (`sdk` names its spec `Ounce`), NVN2. Nintendo EPD's engine (sead / agl / gsys, Phive, Havok 2023.2), modules `main` + `subsdk0` (NintendoSDK movie) + `subsdk1` (`nn::ecli`, Nintendo's embedded Mono runtime) + `sdk`. **In bring-up, not playable:** the earlier base build reached its first frames on the Mac and on the arm64 Android emulator and stopped there on its sparse textures; on the phone its image allocations ran out ([Open](#open)). 1.8.0 has its profile, rewrite and Android shader library; on the phone it starts `nnMain` ([Boot (Android; 1.8.0)](#boot-android-180)). Its closest relative here is [Donkey Kong Bananza](../040074A01BF12000/README.md) (same engine, NVN2, Ampere shader code).

## Boot (Android; 1.8.0)

Phone, 2026-11-03 (Honor PNM-N49, Adreno 840, system driver; test app `dev.nxnative.android.mkw` from `android-mkw2` f68cff94, `-PnxApp=mkw`; pack `Switch2/0400C3F00006E000-work/android-pack-1.8.0`, the dump at `Switch2/MarioKartWorld/base`, a new save folder): the modules load (subsdk0 and subsdk1 at their own bases, 924 of sdk's symbols bound to earlier modules), the heap is 7.47 GB in a 7.50 GB heap region (the formula above held), `nnMain` starts, the RomFS mounts, NVN2 device API 231.30 (SDK 21), and then, within 2 s of `nnMain`, the main thread stops: `CRASH sig=11 addr=0x20 pc=main+0x69c020`, right after it started the "Prepare Thread" (last svc 0x9). No frame, no image made, so the image allocations were not reached; RSS was not sampled (the process ended inside the first 2 s window).

- The fault: `main+0x69bfd0` (a virtual function, slot 0xc0 of the vtable at `main+0x367a9e0`) loads the global at `main+0x37be900` (through the GOT slot `main+0x36d3a48`) and calls through its +0x20 without a null check; the global was still 0. **Cause (resolved):** the game creates its graphics system, the object that global holds, only when NVN reports major 231 and minor 39 or more (`main+0xdd0890`, then the 0x260-byte allocation and the store at `main+0xdd0900`), and the host answered 231.30. NVN2's versions move with the SDK (21.4.0's sdk answers 231.39 and GPU code minor 20); the host now reads them from the game's own `sdk` (`dm_sdk_nvn2_item`, from upstream nxnative c8521eeb: [The Switch 2's device values](../../../docs/reference/nvn-objects.md#the-switch-2s-device-values)). Not a scheduling problem: the reader and the writer are both on the main thread.
- After that fix (a772aae3; retries m2-m4, 2026-11-03): NVN reports 231.39, the graphics system comes up (window 3840x2160, 3 textures; 2.83 GiB of pools placed, 60 pools, RSS 6.6-6.8 GB within 8 s), and the boot stopped in turn on three SDK calls that reach services the host does not serve: `nn::hid` Jcms / Nmouse (abort 0xe15; hooked, e37131ab), `nn::chat::AttachToRoomInfoChangedEvent` (a null read at `sdk+0x6bc148`; hooked with the sharing key calls, ddb59130), and now (current) `nn::chat::CalculateLocalCameraVideoBufferSize` aborts (`sdk+0x6bf2c8`): it checks GameChat's initialize count (`sdk` data through `[sdk+0xe28038]`), which stays 0 because the host takes over `nn::chat::Initialize`. ## Next on the phone

In the order they block. Line numbers are those of `dm/gfx/vk_android/vka_tex.c` at ba792d46.

1. **Image sub-allocator: done; on the phone with Donkey Kong Bananza, not yet reached by this game.** Every image had a `VkDeviceMemory` of its own (`VkMemoryDedicatedAllocateInfo`); the earlier build's images failed with `-2` from about 2,300 on, beside 1,732 pool segments. The device reports no allocation count limit (`maxMemoryAllocationCount` 4294967295), so the cause of those failures is open; fewer allocations is still the change to make first, since each is a kernel GPU object. Now `vka_imgmem.c` puts every image under 4 MiB that the driver does not want dedicated (`VkMemoryDedicatedRequirements`) into a 64 MiB block of its memory type: exactly the 256-byte units its size needs, at its alignment, first fit (`vka_extents.h`, tested by `dm/host/tests/t_android_imgmem.c`).
